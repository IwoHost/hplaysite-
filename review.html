Hplay

A classic click-wheel music player, rebuilt from scratch for Android, and handed to its first alpha tester today.

v38.0 “Barney” alpha 60 days old 69 commits Android

It started on 16 July 2026 at 1,703 lines. Sixty days later it is 3,520 lines, has 50 screens, plays video, spins a vinyl record with a tonearm that tracks inward as the song runs down, and keeps a year of listening history it never sends anywhere.

The thing that makes it unusual is the constraint. No framework, no component library, nothing pulled in from a package manager. The click wheel physics, the audio graph, the library storage, the marketplace client: all of it written by hand, and all of it shipping as an app you install on a phone.

Four Hard Problems

Every project has a few problems that take far longer than they should. Here are four of them.

The tonearm that kept sinking

A transform is enough to trap a z-index

The tonearm has to paint above the text panel that the record slides behind. It had z-index: 3, which should have settled it, and it kept disappearing anyway.

The cause is a CSS rule that catches people out. A transform, a filter or a will-change on an ancestor creates a stacking context, and a child's z-index can never escape it. Removing the wrapper's own z-index wasn't enough, because the base artwork rule re-applied a sway animation, and an animated transform does the same thing. The fix was an explicit animation: none on the vinyl container. It looks like a line that does nothing.

The record that stuttered once a second

Don't re-derive an animation's phase. Carry it.

Now Playing rebuilds itself every second, so the spinning record restarted every second too. The obvious fix was to compute where the record should be from the track position and set the animation delay to match. It stuttered: the disc jumped a degree or two, every second, forever.

CSS animations don't start the instant you insert the element. They start a frame later, and that one frame of drift compounds against a clock taken from somewhere else. The answer was to stop deriving anything and carry each animation's own currentTime across the rebuild via getAnimations(). After that it measured steady to within 17 milliseconds.

The backdrop that never advanced

The engine won't decode a video nobody can see

The plan for video was to sample frames onto a canvas and blur them behind the screen. It produced exactly one frame and then froze. The video element was tried at one pixel, at sixty-four pixels, at zero opacity, at one percent opacity, behind everything in the stacking order. Same result every time.

Chrome stops producing frames for a video that isn't really being rendered, and hiding it more cleverly can't help, because the hiding is the problem. So the whole approach went in the bin. Instead a second, silent copy of the file plays as the backdrop, nudged back into step whenever it drifts more than a third of a second.

The screen that changed size

Absolute positioning measures from the padding box

Playing an MP4 made the screen appear to grow, with a second set of corners inside the bezel. It looked like a rendering glitch. It was arithmetic.

The video stage was inset: 0 inside the bezel. But an absolutely positioned box measures from its ancestor's padding box, not its content box. The bezel has 3vw of padding for the black border, so the picture spread 12.6 pixels past the screen on every side and painted its own corners out in the trim. Both now share the padding as one variable.

The State Of It

An honest read, on the day it goes to someone else for the first time. It's an alpha, and the list on the right is why. A real, working player with real holes in it.

Solid

  • Playback, the click wheel and navigation are stable and have been for weeks.
  • Settings are defined in one table, so adding one is a single edit. It used to be seven.
  • All 24 settings round-trip through storage, reject rubbish, and survive a reload. Checked automatically, not by hand.
  • Every screen mode is legible selected and unselected, measured against a contrast ratio rather than eyeballed.
  • Usage data stays on the device, can be switched off, and can be wiped.
  • It survived a month of neglect and picked straight back up.

Rough

  • Song IDs are regenerated on every folder rescan, but playlists and the resume point store IDs. A rescan while music is playing can break next and previous. This is the most important thing left to fix.
  • Deleting a song from a scanned folder doesn't stick; it comes back on the next scan.
  • There's no export or backup. Everything lives in one database on one phone.
  • Resume-on-restart doesn't work yet.
  • The build the testers have is five changes behind the current one, including the file filter that lets video through.
  • No test suite in the repo. The checks exist, but they live outside it.
